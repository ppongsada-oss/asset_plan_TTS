# Agent Harness Workflow — คู่มือการทำงานฉบับสมบูรณ์ (End-to-End Reference)

เอกสารฉบับนี้สรุปกระบวนการทำงานของ Agent Harness ในระบบ **Asset Plan** อย่างละเอียด ตั้งแต่เริ่มต้นจนสิ้นสุดเซสชัน สำหรับอ้างอิงขั้นตอนและกลไกภายในระบบ

---

## 1. จุดเริ่มต้น: เมื่อ User ส่งคำสั่งงาน (Entry Point)

เมื่อ User พิมพ์งานเข้ามา ระบบจะเริ่มต้นด้วยขั้นตอน **Boot Sequence** และ **Per-Turn Routing** ทันที ดังนี้:

### A. Boot Sequence (จำกัด Tool Call สูงสุด 3 ครั้ง)
เมื่อเริ่มต้นเทิร์นแรกของงาน ระบบจะทำงานตามลำดับโดยอัตโนมัติ:
1. **[B1] อ่านสถานะเดิม**: รัน Bash เพื่อเช็คสถานะจาก `.sessions/active_thread.md`
   - หาก `phase` ไม่ใช่ `in_progress` (เป็น `done`) จะทำการรีเซ็ตค่าโทเค็นสะสม (`SESSION_TOTAL: 0`) ใน `.sessions/session_tokens.md`
   - พิมพ์งานที่ค้างในระบบจาก `docs/master_roadmap.md` ออกมาดู
2. **[B2] ตรวจหา Skill ที่สอดคล้อง**: อ่านไฟล์ `.agents/skills/skill-manifest.json` เพื่อนำข้อความคำสั่งของ User ไปจับคู่กับ Keyword เพื่อค้นหา Skill ที่ต้องใช้ (เช่น `coder`, `editor`, `session_manager` เป็นต้น)
3. **[B3] โหลดโครงสร้างและ Context**: อ่านไฟล์ข้อกำหนดของ Skill นั้นจาก `.agents/skills/<skill_name>/SKILL.md` เพื่อนำ `sections[]` (ขอบเขตงานย่อย) และ `context_files` (ไฟล์ที่เกี่ยวข้อง) เข้าสู่หน่วยความจำ
4. **[B4] ระบุแพลตฟอร์มเครื่อง (กรณีไม่ทราบ)**: รันการ Probe ตรวจหาเครื่องมือและ OS หากไฟล์ `.agents/platform/detected.md` ระบุแพลตฟอร์มเป็น `unknown`

**การตอบกลับในบรรทัดแรกสุด (Mandatory Reply Line 1):**
ทุกครั้งหลังจากเสร็จสิ้นขั้นตอนการ Boot ระบบจะต้องแสดงข้อความ Boot Trace ในบรรทัดแรกของคำตอบเสมอในรูปแบบ:
`**[Boot]** Thread: <done|in_progress> · Tasks: <N open> · Skill: <name> · Sections: <N> · Tokens: ~<N>k`

### B. Per-Turn Routing (การตรวจสอบทิศทางงานทุกรอบการสั่ง)
ระบบไม่ยอมรับการคงสถานะ Skill เดิมแบบเหมาจ่าย ทุกครั้งที่ User พิมพ์ข้อความใหม่เข้ามา ระบบจะเข้าสู่การเช็ค Intent:
- **C1**: ดึง Intent Keywords จากข้อความล่าสุดของ User
- **C2**: เทียบ Keyword กับไฟล์ `skill-manifest.json`
- **C3**: หาก Skill ตรงกับที่โหลดไว้เดิม ระบบจะทำงานต่อเงียบๆ หากเปลี่ยนไปเป็นอีก Skill ระบบจะโหลดข้อกำหนดใหม่และพ่นข้อความ Trace `**[→ skill]**` ทันที

## 2. ขั้นตอนการเลือกและเปลี่ยน Skill (Skill Selection)

ระบบจะจับคู่คำสั่งและ Intent ของ User เข้ากับ Skill ต่างๆ ดังนี้:

| Intent ของ User | Skill ที่เลือกรัน | บทบาทและหน้าที่ |
| :--- | :--- | :--- |
| ตรวจแก้บั๊ก / แก้โค้ด / จัดการ Error | `editor` (Code Editor) | แก้ไขและดีบั๊กไฟล์เดิมในระบบแบบผ่าตัดรายบรรทัด |
| สร้างไฟล์ใหม่ / เพิ่มฟีเจอร์ / ทำหน้าใหม่ | `coder` (Coder Creator) | สร้างไฟล์ ตั้งโครงสร้างระบบ และเขียนโค้ดใหม่ |
| ย้าย ย้ายชื่อ ลบไฟล์ หรือเปลี่ยน Import | `file_manager` | จัดการไฟล์และสืบหาความสัมพันธ์ของไฟล์ (Backlinks) |
| สร้าง เปลี่ยนชื่อ หรือลบตัวแปร/ฟังก์ชัน | `variable_manager` | ติดตามและอัปเดต Variable/Function Index ในระบบ |
| สั่ง "ปิด session", "จบงาน", "done", "close" | `session_manager` | บันทึกประวัติเซสชัน รีเซ็ตค่าโทเค็น และเขียนสรุปส่งท้าย |
| คำสั่งอื่นที่ไม่มี Keyword ตรงตามกำหนด | `agent` (Fallback) | โหลด `registry.md` เพื่อเลือกแนวทาง orchestration |

## 3. สถาปัตยกรรมลูป (Loop Architecture — 3 Phases)

เมื่อมีงานที่ซับซ้อนเข้ามา (> 3 ขั้นตอน หรือมีผลกระทบกับไฟล์/DB) ระบบจะเข้าสู่ Loop Architecture 3 เฟส:

### Phase 1: Info Gather Loop (การเก็บข้อมูลก่อนเริ่มงาน)
เป็นการรันลูปย้อนกลับไปกลับมา (G1 → G2 → G3) สูงสุด 3 รอบ เพื่อรวบรวมบริบทให้เพียงพอ โดยมีเงื่อนไขผ่านด่าน (**context_sufficient checklist**) 3 ข้อ:
1. ทุกข้อกำหนด (Sections) ของ Skill นั้น มีข้อมูลพาธไฟล์หรือสัญลักษณ์จาก Index อย่างน้อย 1 รายการ
2. ทุกข้อกำหนดมีเกณฑ์วัดผลสำเร็จที่รันจริงได้และคาดหวังผลลัพธ์ได้ชัดเจน (Draft `Verify-N` criterion)
3. ไม่มีเครื่องหมายคำถามหรือจุดที่ยังไม่กระจ่างค้างอยู่
- หากครบถ้วน: แสดง Trace `**[✓ gather]**` และเข้าสู่ Phase 2
- หากไม่ครบใน 3 รอบ: แสดง Trace `**[gather-stalled]**` และหยุดรอถาม User ต่อ

### Phase 2: MECE Plan (การวางแผนรอบคอบแยกส่วนเด็ดขาด)
รันเพื่อแตกงานออกเป็นส่วนๆ ที่ไม่ซ้ำซ้อนกันและครอบคลุมงานทั้งหมด:
1. **[M1-M2] สร้างแผน**: โหลดแผน MECE และแปลงเป็นข้อกำหนด (Sections) แบบ 1:1 ตามโครงสร้างของ Skill
2. **[M2.5] กำหนดเกณฑ์ Definition of Done (DoD)**: กำหนดคำสั่ง Verify ที่ใช้รันตรวจสอบทางเทคนิค เช่น:
   - `Verify-1`: `grep -c "export default" src/app/page.tsx` → expected: 1
   - `Verify-2`: `npm run build` → expected: exit 0
3. **[M3] ขอการอนุมัติจาก User**: ส่งขั้นตอนและเกณฑ์ตรวจสอบให้ User กดยืนยัน (ห้ามทำงานก่อนได้รับคำยืนยันเด็ดขาด)
4. **[M4-M5] ลงแผนและเริ่มทำงาน**: เขียนแผนลงใน `.sessions/mece_plan.md` และบันทึกคำสั่งใน `docs/master_roadmap.md` จากนั้นแสดง Trace `**[✓ MECE]**`

### Phase 3: Execution Loop (การลงมือรันงานแบบ React Loop)
รันทีละ Section ของแผนงานด้วยลูปแบบ **SELECT → EXECUTE → OBSERVE → VERIFY → DECIDE (L1-L5)**:
- **[L1] SELECT**: เลือกเครื่องมือที่แคบที่สุดในการทำ (รันตามลำดับความสำคัญใน Index)
- **[L2] EXECUTE**: ทำการแก้ไขโค้ดหรือเรียกใช้งาน Tool (จำกัดผลลัพธ์ Tool ไว้ที่ 300 บรรทัด)
- **[L3] OBSERVE**: สังเกตผลที่เกิดขึ้น หากผิดพลาดให้อ่านและดีบั๊กแก้ปัญหา 1 ครั้ง
- **[L4] VERIFY**: 
  - (a) ตรวจสอบการบันทึกไฟล์ด้วยคำสั่ง Grep เสมอเพื่อให้แน่ใจว่าเขียนไฟล์สำเร็จจริง แสดง Trace `**[✓ written]**`
  - (b) รันคำสั่ง `Verify-N` ที่เตรียมไว้ในเฟสวางแผน
- **[L5] DECIDE**: การจะถือว่า Section นั้นเสร็จสิ้น ต้องผ่านทั้ง (a) ตรวจสอบไฟล์เขียนสำเร็จ และ (b) รันคำสั่ง Verify ผ่าน หากไม่ผ่านจะถือว่าล้มเหลวและต้องทำซ้ำ

## 4. ระบบการแยกงานขนานและ Sub-Agent (Cycle Orchestration)

หากแผน MECE มีขั้นตอนย่อยที่ไม่มีความเกี่ยวข้องกัน ระบบจะนำมารันพร้อมกันในแบบ **Cycles**:
1. แผนงานจะระบุการรันขนานใน Cycle เดียวกัน (เช่น Cycle 1 ทำ Section 1 และ 2 ไปพร้อมกัน)
2. ระบบตรวจสอบสถานะเครื่องพิมพ์คำสั่งผ่านแพลตฟอร์ม เพื่อเรียกใช้ **Sub-Agents** ช่วยทำงานย่อยนั้นแยกต่างหาก
3. Sub-Agent แต่ละตัวจะได้รับบริบทที่แคบ (Context Trim) พร้อมคำสั่งรันเฉพาะทาง และเมื่อทำงานเสร็จจะต้องส่งผลลัพธ์กลับมาในรูปแบบไฟล์ JSON เช่น `.sessions/cycle_N_<section_id>.json`
4. เมื่อทุกตัวในรอบนั้นส่งผลสำเร็จ ระบบจะตรวจสอบความถูกต้องของ JSON แล้วจึงรวบรวมข้อมูลรัน Cycle ถัดไป
5. **ข้อจำกัดสูงสุด**: Sub-Agent ทำงานในความลึกจำกัดสูงสุดแค่ระดับเดียว (Depth = 1) และจำนวนประวัติแชทต้องไม่เกิน 5 ข้อความเพื่อลดการใช้โทเค็น

## 5. การจัดการสิทธิ์และกฎความปลอดภัยของข้อมูล (Gates)

ก่อนดำเนินการที่อาจส่งผลเสียต่อระบบ ระบบจะผ่านกระบวนการกลั่นกรอง 3 ระดับ:
- **[gate] การทำงานที่อาจสร้างความเสียหาย (Destructive Action Gates - R14)**: เช่น การลบหรือเขียนทับไฟล์ใน `src/` หรือ `knowledge/`, การแก้ไขโครงสร้าง DB หรือคอลัมน์ ระบบจะหยุดการทำงานและพิมพ์ข้อความขอความเห็นชอบ เช่น `[gate] Action: ...Scope: ...` และต้องรอให้ User พิมพ์ยืนยันจึงจะไปต่อได้
- **[db-gate] การแก้ไขฐานข้อมูล (DB Structure Hard Stop - R15)**: สำหรับการแก้ไขไฟล์ใน `src/db/` ทุกกรณี หรือแก้ไขประเภทตัวแปรของ Drizzle ORM ระบบจะสั่งหยุดทำงานทันทีและพิมพ์คำชี้แจงความเสี่ยงพร้อมรอ User พิมพ์ "yes" ยืนยันคำเดียวเท่านั้น
- **[R9] การตรวจสอบบั๊กและเออร์เรอร์ (Error Protocol - R9)**: ก่อนดำเนินการตรวจแก้ใดๆ ต้องเรียกหา 3 สิ่งตามลำดับ: 
  1. ค้นหาคีย์เวิร์ดใน `knowledge/error_index.md` 
  2. ตรวจสอบ Symbol ใน `knowledge/index_variables.json`
  3. ค้นหาไฟล์อ้างอิงใน `knowledge/index_files.json` เพื่อวิเคราะห์ขอบเขตผลกระทบ (Blast Radius) เมื่อเช็คครบจึงแสดง Trace `**[✓ R9]**`

## 6. การควบคุมโทเค็นและเซสชันสะดุด (Token & Pause Protocol)

เพื่อรักษาระดับการใช้โทเค็นไม่ให้บานปลายและควบคุมงบประมาณ:
- **โทเค็นสะสม (SESSION_TOTAL)**: จะถูกประมาณการในหน่วยความจำทุกการพิมพ์ (ตามสูตรของ R1) และจะอัปเดตลงไฟล์เฉพาะจุดสำคัญ
- **งบประมาณสะสม (Thresholds)**:
  - **> 50k tokens**: ระบบจะรันคำสั่ง **Mid-Session Compact** อัตโนมัติ (ไม่ขัดจังหวะการทำงาน) เพื่อล้างประวัติการใช้ Tool ที่ยาวเกินจำเป็นออกไป
  - **> 60k tokens**: เมื่อสิ้นสุดเทิร์นปัจจุบัน ระบบจะเซฟสถานะปัจจุบันทั้งหมดลงใน `.sessions/session_handoff.md` และหยุดชั่วคราว (**TOKEN PAUSE**) พร้อมแสดงข้อความ Trace `**[pause]**` และถามผู้ใช้ว่า "ดำเนินการต่อไหมครับ?"
  - **> 90k tokens**: สั่ง **HALT** หยุดการทำงานทันทีเพื่อป้องกันความเสียหายทางการเงิน

**ขั้นตอนการกู้สถานะหลังโทเค็นหยุด (Resume Protocol):**
เมื่อผู้ใช้กดตอบรับให้ทำต่อ ระบบจะทำการโหลดประวัติและ context ใหม่ โดยมีสิทธิ์รีโหลด config ไฟล์ขึ้นมาอีกครั้ง รักษาสิทธิ์แผน MECE เดิม และเริ่มต้นทำงานต่อจาก Section ที่ค้างไว้ทันที โดยในเซสชันใหม่จะมีงบทำซ้ำแบบจำกัดความเสี่ยง (Attempt Count = 1) หากพลาดอีกครั้งจะขึ้นสถานะ Blocked ทันที

## 7. ข้อจำกัดและมาตรการหยุดเมื่อทำงานพลาด (Blocked Flow)

ระบบมีกลไกป้องกันการลองผิดลองถูกซ้ำซากเพื่อจำกัดความเสียหาย:
- ในการแก้ปัญหาหนึ่งๆ ระบบจะจำกัดการทำซ้ำไว้ที่ 2 ครั้ง (**Attempt Limit**)
- หากเกิดความล้มเหลวซ้ำในขั้นตอนเดิมเป็นครั้งที่สอง (AttemptID = 02) ระบบจะสั่ง **HALT** เซสชันย่อยนั้นและปรับสถานะในระบบเป็น **Blocked** ทันที
- ระบบจะอัปเดตสถานะลง `.sessions/session_handoff.md` ด้วยสถานะ `status: blocked`
- แสดงความเสียหาย แผงงานส่วนที่ทำสำเร็จแล้ว และส่วนที่ยังค้างอยู่ ให้ User พิจารณา
- ถามผู้ใช้ด้วยข้อความ: `"แก้ก่อนดำเนินการต่อ หรือ skip section นี้?"` และจะรอการตอบกลับโดยไม่พยายามดีบั๊กโค้ดต่อด้วยตัวเอง

## 8. การสรุปและปิดงาน (Completion Gate & Session Close)

### A. Completion Gate (ด่านผ่านสำหรับการเสร็จงาน)
ระบบไม่สามารถระบุว่างานเสร็จสิ้นหากขาด 7 เช็คลิสต์นี้:
1. ข้อกำหนดทั้งหมดในแผน MECE ได้รับการรันเครื่องมือทดสอบจนครบหมด (ไม่ใช่แค่คาดการณ์)
2. ทุกไฟล์ที่บันทึก/แก้ไข ได้รับการตรวจสอบการมีอยู่ผ่าน Grep สำเร็จแล้ว (`[✓ written]`)
3. ทำการอัปเดตดัชนีผ่าน `python scripts/symbol_indexer.py` แล้ว
4. งานในแผนงานหลัก `docs/master_roadmap.md` ได้รับการมาร์กสถานะเป็นเสร็จสมบูรณ์ `[X]`
5. ไฟล์ `.sessions/active_thread.md` ระบุสถานะ `phase: done`
6. ไฟล์ `.sessions/session_tokens.md` มีค่าโทเค็นสรุปสะสมบันทึกอยู่
7. พิมพ์ตารางสรุปผล และข้อแนะนำสำหรับกรณีพบรูปแบบการเขียนโค้ดที่มักจะผิดบ่อยเพื่อลงใน `CODING_FAILURE_PATTERNS.md`

### B. Session Close (ขั้นตอนปิดการเชื่อมต่อเซสชัน)
เมื่อ User สั่งคำสั่งปิดงาน เช่น "ปิด session" ระบบจะส่งต่อให้ `session_manager` รับหน้าที่เขียนไฟล์บังคับ 4 ไฟล์ เพื่อเตรียมการเปิดเซสชันใหม่ในครั้งหน้า:

| ไฟล์ที่เกี่ยวข้อง | สิ่งที่ต้องเขียนบันทึก |
| :--- | :--- |
| **Active session JSON**<br>(เช่น `.sessions/session_073_theme.json`) | บันทึกสถานะ `"status": "completed"` และพิมพ์รายละเอียดสรุปผลของเซสชันที่ `"summary_context"` |
| **.sessions/session_tokens.md** | ปรับค่าโทเค็นสะสมกลับไปเป็น `SESSION_TOTAL: 0` เพื่อเตรียมสำหรับงานถัดไป |
| **.sessions/active_thread.md** | บันทึก `phase: done` และระบุความคืบหน้าของ Task ล่าสุด |
| **.sessions/session_handoff.md** | เขียนสถานะสรุป `status: completed` และแนะนำก้าวถัดไปเมื่อเริ่มต้นระบบใหม่ |

เมื่อเขียนครบ 4 ไฟล์แล้ว ระบบจะแสดงความพร้อมในการจัดเก็บข้อมูลลง Git และตอบกลับด้วยข้อความปิดเซสชันในรูปแบบ:
```
Session ปิดแล้วครับ — ไฟล์ที่บันทึก:
· .sessions/session_<NNN>_<topic>.json → status: completed
· .sessions/session_tokens.md → SESSION_TOTAL: ~<N>k
· .sessions/active_thread.md → phase: done
· .sessions/session_handoff.md → next: <summary>
```
